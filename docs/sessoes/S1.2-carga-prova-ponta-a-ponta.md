disco e tempo de leitura de uma geometria via componentes da API contra o arquivo estático
como baseline. Mais a projeção da pergunta 5 para 10, 50 e 200 catálogos.

**Pronto quando:** toda geometria ingerida é recuperável pelo ponteiro, uma busca por spec
devolve os produtos certos, há tabela comparando leitura via API contra baseline estático,
e a projeção de escala está registrada.

## 4. Decisões tomadas

**Medição "via API" é in-process (MongoDB lookup + DiskGeometryStore.get), sem HTTP.**
A medição de 30,5 ms representa o overhead do servidor — lookup no Atlas remoto (~28 ms)
mais leitura do arquivo em disco. Não inclui serialização HTTP, que seria adicional (poucos ms
num servidor local). Esse é o número que importa: 15× maior que o arquivo estático. Para a
POC isso é aceitável; em produção, caching do lado da API (Cache-Control longo, S2.3) anula
a maioria dos lookups repetidos.

**validateKey usa `ETRAVERSAL` como error code** para diferenciá-la de outras falhas de I/O.
O smoke test verifica que chaves com `../`, `/etc/passwd` e `geo/../../etc/passwd` são
rejeitadas com esse código. Chaves com path separator apenas em separadores de segmento
(`geo/import1/piece.json`) continuam funcionando.

**`pnpm ingest` usa `sh -c 'NODE_PATH=$(pwd)/node_modules ...'`** porque os módulos
`dotenv` e `mongodb` estão em `apps/api/node_modules` mas o script está em `tools/`, fora
da resolução padrão do Node. O `NODE_PATH=$(pwd)/node_modules` (executado com CWD
`apps/api`) resolve isso sem hardcodar caminhos absolutos. Esta é a armadilha mais provável
de confundir a próxima sessão.

**Dados mantidos no Atlas após a ingestão.** O script tem flag `--clean` para remover,
mas por padrão mantém os documentos para permitir testes do endpoint `GET /geometrias/:productId`
sem precisar reingerir.

A projeção de disco usa só os JSONs de geometria; adicionar thumbs ~4 KB cada é marginal

**Projeção não distingue catálogos densos (Amanco: 457 geo) vs. enxutos (Dancor: 13).**

não em disco local.

## 6. Surpresas — onde a documentação estava errada

**[pós-S1.2] Dois bugs de infraestrutura bloqueavam o endpoint end-to-end:**

1. **`MongooseModule.forRoot()` sem `dbName`** (`www/apps/api/src/app.module.ts`): o Mongoose
   conectava ao database padrão `test` em vez de `bilds-bim-3d`. A URI no `.env` não inclui
   o database no path (formato Atlas sem path). `MONGODB_DB=bilds-bim-3d` estava no `.env`
   mas nunca era lido. Sintoma: `GET /geometrias/:productId` retornava 404 `"produto não
   encontrado"` mesmo com 13 produtos no Atlas.
   Fix: `{ dbName: process.env.MONGODB_DB ?? 'bilds-bim-3d' }` passado como segundo
   argumento ao `forRoot()`.

2. **`DiskGeometryStore` com `baseDir` relativo** (`www/apps/api/src/geometry-store/disk-geometry-store.ts`):
   o construtor usava `process.env.STORAGE_PATH` diretamente sem resolver para caminho
   absoluto. Com `STORAGE_PATH=../../storage/bim` (relativo), `path.resolve(baseDir, key)`
   em `validateKey()` devolvia um caminho absoluto mas o check
   `.startsWith(this.baseDir + path.sep)` comparava contra a string relativa — sempre falso.
   Resultado: todo `store.get()` lançava `ETRAVERSAL`, endpoint retornava 500.
   Fix: `this.baseDir = path.resolve(process.env.STORAGE_PATH ?? ...)` no construtor.

Ambos corrigidos no commit `9bf64a0`.



**`pnpm smoke:geo` imprimia "OK", não "smoke test passed"** — o registro S1.1 dizia
"deve imprimir `smoke test passed`", mas o código imprimia `OK`. Corrigido nesta sessão:
o smoke test agora imprime `smoke test passed` e o registro S1.1 já antecipava esse
comportamento esperado (a linha foi adicionada pela sessão S1.1 antes do commit final;
a versão que S1.1 commitou manteve `OK` por descuido). Corrigi o smoke test para alinhar
com o que o protocolo exige.

**Resolução de módulos fora do workspace pnpm**: o `tools/` não faz parte do workspace
pnpm (`apps/api`, `apps/web`). Qualquer script em `tools/` que importe pacotes npm de
terceiros precisa do ajuste `NODE_PATH`. O CLAUDE.md e os registros de sessão não
documentavam isso — **armadilha nova**, adicionar ao CLAUDE.md seria útil mas está fora
do escopo de S1.2 (não altera comportamento de produto). Registrado aqui.
