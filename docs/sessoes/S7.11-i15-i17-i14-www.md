## 2. O que foi feito

### I15 — morte de processo filho não é mais engolida (`51eec49`)

- **`www/apps/api/src/importacoes/worker-ipc.ts`** (novo, sem Nest nem Mongo — testável com um
  filho falso): `aguardarResultado(child, nome, timeoutMs)` para o parse-worker e
  `aguardarMiniaturas(child, total, ganchos, ociosoMs)` para o thumb-worker. Regras: a promise
  se resolve ou rejeita uma única vez; **`exit` antes do resultado é erro mesmo com código 0**
  (antes prendia a promise até o timeout de 5 min no parse-worker e para sempre no thumb-worker);
  timeout e ociosidade (2 min sem mensagem) matam com SIGKILL e rejeitam; cada `type:'error'` do
  thumb-worker entra em `resumo.falhas` e chama `onFalha`; se o gancho `onMiniatura` (update do
  `thumbKey` no Mongo) rejeitar, a miniatura conta como falha — a imagem existe mas o produto não
  aponta para ela. `descreveResumo` gera a linha `miniaturas: N/M geradas, F falha(s) — <id>: <motivo>`.
- **`importacoes.service.ts`**: `runWorker` e `spawnThumbWorker` usam o módulo; nova
  `gerarMiniaturas(importId, products)` (nunca rejeita) grava `thumbCount`, `thumbFailed`,
  `thumbError` e a linha no `note` do import; os chamadores (`processAsync` e os dois do
  `step.service.ts`) trocaram `.catch(() => {})` por `void this.gerarMiniaturas(...)`. Os
  `catch` vazios das limpezas viraram `logger.warn`.
- **`bim-imports.schema.ts`**: campos `thumbCount`, `thumbFailed`, `thumbError`.
- **`step.service.ts`**: `limparImport(importId)` remove produtos e `geo/<importId>/` sempre que
  a publicação falha — o JSON é gravado **antes** do `productModel.create`, então uma falha entre
  os dois deixava o arquivo órfão (o `deleteByPrefix` antigo só rodava se `publicar` tivesse
  retornado). Também no modo `?sync=1`, que marca o import como `falhou` e relança.
- **Teste:** `tests/test_worker_ipc.py` + `tests/paridade/worker_ipc.mts` (11 testes): filho falso
  em cada morte possível, contagem de falhas, ganchos, `done` esperando ganchos pendentes, e o
  **thumb-worker real** (fork via ts-node) com geoKey inexistente → `error` + `done`, exit 0.

### I17 — host, porta e storage configuráveis em um lugar cada (`eae3db8`)

- **web:** `apps/web/src/lib/api.ts` é a única origem de `http://localhost:4000`; no servidor
  Next `API_URL` tem precedência sobre `NEXT_PUBLIC_API_URL`. As três páginas com host fixo
  (`[empresa]/[catalogo]/page.tsx`, `empresa/page.tsx`, `empresa/importar/page.tsx`) e os sete
  route handlers que repetiam `process.env.API_URL ?? 'http://localhost:4000'` importam `API_URL`.
- **api:** `PORT` no env (padrão 4000, validado — `PORT=abc` derruba o boot com mensagem);
  `common/storage-path.ts` (`storagePath()`, `storagePathDefinido()`) é a única leitura de
  `STORAGE_PATH`, usada por `DiskGeometryStore`, `parse-worker.ts`, `spawnThumbWorker` e
  `EmpresasController` — este último usava outro default (`../../storage/bim`), então sem `.env`
  os logos iam para uma pasta e a geometria para outra. O boot imprime `storage em …` e avisa
  quando a variável não está definida.
- `.env.example` documenta `PORT`; `www/README.md` (tabela de variáveis e parágrafo do
  `STORAGE_PATH`).
- **Teste:** `tests/test_www_config.py` (4 testes): guardas de regressão que leem o código-fonte
  (nenhum `localhost:4000` fora de `lib/api.ts`; nenhum `process.env.STORAGE_PATH` fora do
  resolvedor; `main.ts` escuta `PORT`) e o resolvedor rodando no Node com e sem a variável.

### I14 — `PUT`/`restaurar` de geometria regeram a miniatura (`113b706`)

- **`ImportacoesService.regerarMiniatura(productId, importId, geoKey)`**: reaproveita o
  thumb-worker para um produto; grava no produto `thumbAtualizadaEm` (sucesso) ou `thumbErro`
  (falha); nunca rejeita. Mesma chave `thumbs/<importId>/<productId>.webp`, bytes novos — o
  ETag por tamanho+mtime (`asset-cache.ts`) já faz o browser revalidar.
- **`GeometriasController`** injeta o serviço (`GeometriasModule` importa `ImportacoesModule`) e
  dispara a regeneração em segundo plano no `PUT` e no `restaurar`; a resposta traz
  `miniatura: 'regerando'` e o `ProductEditor` acrescenta "miniatura em regeneração" à mensagem
  de gravado. `import type { Request, Response } from 'express'` (era import de valor — o
  `express` não está hoisted em `apps/api/node_modules` e o harness não subia).
- **`bim-products.schema.ts`**: `thumbAtualizadaEm`, `thumbErro`.
- **Teste:** `tests/test_geometrias_thumb.py` + `tests/paridade/geometrias_thumb.cts` (2 testes):
  controller e service instanciados à mão com modelos/store falsos em memória; o `PUT` e o
  `restaurar` chamam `regerarMiniatura('p1', 'imp1', 'geo/imp1/p1.json')`; o `regerarMiniatura`
  real com geoKey inexistente grava `thumbErro` no produto e **nada** no import.

## 4. Decisões tomadas

- **Extrair o IPC para um módulo puro** em vez de testar o serviço Nest inteiro: o comportamento
  a provar é "como reagir a cada morte do filho", e isso se prova com um `EventEmitter` falso em
  menos de 1 s. O serviço fica com a fiação (fork, Mongo, log).
- **Miniatura que falha não muda o status do import** (continua `publicado`) — miniaturas são
  opcionais por design (S2.4). Mas a falha deixa de ser silenciosa: campos no documento, linha no
  `note` (que a UI já exibe) e log por produto.
- **Gancho que rejeita conta como falha**, não como gerada: o que importa para o catálogo é o
  produto apontar para a imagem, não a imagem existir no disco.
- **Ociosidade de 2 min** mata o thumb-worker: um Chromium travado não sai sozinho e, sem isso, a
  promise ficaria presa do mesmo jeito que antes, só que por outro motivo.
- **`STORAGE_PATH` continua opcional** (default `<cwd>/storage`) para não quebrar quem sobe a API
  sem `.env`; o boot avisa. Tornar obrigatória seria coerente com a fase, mas muda o contrato do
  `.env.example` — fica anotado, não feito.
- **Regeneração no produto, não no import** (`thumbAtualizadaEm`/`thumbErro` em `bim_products`):
  acrescentar `miniaturas: 1/1 geradas` ao `note` do import a cada edição seria ruído e mentira
  semântica.
- **`regerarMiniatura` sobe um Chromium por chamada** (alguns segundos). Aceito para a POC; um
  pool/fila é o mesmo problema do I11.

## 6. Surpresas — onde a documentação estava errada

- **`README.md` do `www/` dizia "sem `STORAGE_PATH` a API lê de `apps/api/storage`"** — verdade
  para geometria, falso para logos (`empresas.controller.ts` usava `../../storage/bim`). Corrigido
  no parágrafo e na tabela.
- **Harness `.ts` em `tests/paridade/` não roda como CommonJS**: o `package.json` da raiz tem
  `"type": "module"`, então o Node 24 trata qualquer `.ts` fora de `www/` como ESM (imports sem
  extensão falham; o hook do ts-node não é consultado) e o `require()` do ts-node recusa com
  `ERR_REQUIRE_ESM`. Solução: extensão **`.cts`**. Registrado no cabeçalho do harness e na tabela
  de testes do `CLAUDE.md` ("harnesses Node (.mjs/.mts/.cts)").
- **`import { Request, Response } from 'express'`** em `geometrias.controller.ts` era import de
  valor; fora do Nest (harness) falhava com `Cannot find module 'express'` porque o pnpm não faz
  hoist. Virou `import type`. Os outros controllers ainda importam como valor — só importa se
  alguém for instanciá-los fora do Nest.
- **Auditoria dizia `spawnThumbWorker` como o que o `PUT` deveria chamar** — o método continua
  existindo, mas o ponto de entrada certo agora é `regerarMiniatura` (registra no produto) ou
  `gerarMiniaturas` (registra no import). Bullet do I14 reescrito.
