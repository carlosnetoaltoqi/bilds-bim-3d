# S6.1 — Validador de cache dos assets servidos do storage

**Data:** 2026-08-31 · **Sessão do plano:** fora do plano (hardening pós-POC) · **Status:** concluída
**Commits:** ver `git log --oneline -1` desta data

---

## 1. O que era para fazer

Fechar a pendência conhecida do `CLAUDE.md`: *"Thumb regenerada no mesmo import não
invalida o cache do browser"*. Pronto quando um `pnpm thumb:regen` sobre o **mesmo**
import faz o browser buscar os bytes novos numa navegação normal, sem hard reload.

## 2. O que foi feito

- **`www/apps/api/src/common/asset-cache.ts`** (novo) — `ASSET_CACHE_CONTROL`,
  `assetEtag(key, stat)` e `ifNoneMatchSatisfied(header, etag)`. O docstring explica o
  porquê de cada escolha; leia antes de mexer.
- **`geometry-store.interface.ts`** — novo `stat(key): Promise<AssetStat>` e o tipo
  `AssetStat { size, mtimeMs }`. Lança `ENOENT` igual ao `get`.
- **`disk-geometry-store.ts`** — implementação do `stat` (`fs.stat`, passando pelo mesmo
  `validateKey` que barra path traversal).
- **`thumbs.controller.ts`** e **`geometrias.controller.ts`** — os dois passaram a:
  1. `stat` na chave (não `get`);
  2. ETag = `sha1(key:size:mtimeMs)`, `Cache-Control: public, max-age=0, must-revalidate`;
  3. responder `304` **antes de ler o blob** quando o `If-None-Match` casa;
  4. só então `get` + `Content-Type` + `send`.

O `ENOENT` é tratado nas duas chamadas (`stat` e `get`) — entre uma e outra o arquivo
pode sumir, e sem isso viraria 500.

## 3. O que foi verificado — e como

API reiniciada em `localhost:4000` (`pnpm dev:api`), web já rodando em `:3000`.

| Verificação | Resultado |
|---|---|

| Condicional com a ETag certa | `304`, corpo vazio |
| Condicional com ETag errada | `200`, 5514 b |

| Custo (3 medições cada) | `200` ≈ 35 ms · `304` ≈ 29 ms — o gargalo é a ida ao Atlas, não o disco |

`2cv-t-220-380v-inc-flg-ir3` com **27.425 triângulos**.

`tsc --noEmit` do `apps/api` limpo. O único erro que aparece
(`tools/aq-reader.ts(203,16) TS2352`) é **pré-existente** — idêntico no `HEAD` anterior.

## 4. Decisões tomadas

**`mtime + size` em vez de hash do conteúdo.** O 304 é decidido antes de ler o blob, e a
geometria tem 2,7 MB: hashear o conteúdo obrigaria a ler o arquivo inteiro só para
responder "não mudou". O preço é uma ETag nova quando os bytes são idênticos mas o mtime
mudou — uma cópia de storage sem preservar timestamps, ou um regen determinístico como o
que rodou aqui (mesmo `sha256`, ETag nova). Custa um `200` extra, **nunca** conteúdo
errado. A troca inversa — hash correto, leitura sempre — sairia mais caro no caminho comum.

**`must-revalidate` em vez de URL com hash.** A alternativa arquiteturalmente melhor é a
URL carregar o hash do conteúdo (`/thumbs/:id?v=<hash>`), mantendo `immutable` honesto e
zero revalidação. Foi descartada **para este repo**: exigiria o hash no `thumbKey` gerado
pelo `thumb-worker`, o `regen-thumbs` gravando no banco (hoje ele deliberadamente não
grava), o `catalogos.controller` emitindo o `?v=`, e migração dos 869 produtos já
carregados — mexer no caminho de import para reconquistar o estado que a S5.2 validou.
Desproporcional numa POC encerrada. **É o padrão certo para a reconstrução na bilds.com,
onde há CDN na frente.**

**Aplicado também à geometria.** `geometrias.controller.ts` tinha o mesmo par
ETag-derivada-da-chave + `immutable`, linha a linha. Hoje não morde porque geometria nunca
é regenerada in-place — a correção do parser em S5.1 foi resolvida com reimport completo —
mas é a mesma armadilha esperando o primeiro regen in-place.

## 5. O que NÃO foi feito, e por quê

- **URL com hash do conteúdo** — ver seção 4. Registrada como o padrão para a bilds.com.
- **Pendência do `GET /geometrias` sem auth** — investigada e **não** aplicada, porque a
  finding como estava escrita é inaplicável. Ver seção 6.
- **Testes automatizados** — a POC não tem nenhum (`find apps/api -name '*.spec.ts'` volta

  encerrada; a verificação está na seção 3, reproduzível por `curl`.

## 6. Surpresas — onde a documentação estava errada

**A pendência do `GET /geometrias` sem auth é inaplicável como está escrita** (regra R2).
O `CLAUDE.md` dizia *"endpoint intencional para a POC; adicionar guard antes de qualquer
exposição de rede"*. Um `AuthGuard` ali **quebra a página pública**: é o viewer no browser
do visitante que busca a geometria, sem token. E `catalogos.controller.ts:22` também não
tem guard — uma requisição anônima já devolve os `geoUrl` de todos os produtos.

O gap real é outro e é maior: **não existe conceito de visibilidade em lugar nenhum.**
`bim-catalogs.schema.ts` não tem campo `status`/`visibility` — o `publicado` que aparece no
`CLAUDE.md` é status do *import* (`importacoes.service.ts:210`), e não há equivalente no
catálogo. E
`catalogos.controller.ts:31` filtra só por `companyId + slug`: **um catálogo fica público
no instante em que existe no banco**, sem a empresa ter decidido publicar. Corrigido na
seção "Pendência conhecida" do `CLAUDE.md`.

Coisa boa que apareceu na mesma leitura: `_id` é `crypto.randomUUID()`
(`bim-products.schema.ts:8`), não `ObjectId` sequencial — não há enumeração por adivinhação.

**Nada mais.** Cheguei a registrar uma segunda surpresa sobre os slugs dos catálogos, e
estava errado: a tabela de estado do `CLAUDE.md` (linhas 97-98) já traz
`bomba-de-combate-a-incencio` (13) e `pvc-esgoto-silentium` (856) na mesma empresa Dancor,
e atribui `publicado` às *importações*, corretamente. Eu tinha chutado um slug
(`amanco/predial`, 404) sem ler a tabela.

## 7. Onde a próxima sessão começa

Não há próxima sessão desta linha — a POC segue encerrada. Quem for reconstruir na
bilds.com deve ler
`docs/solutions/architecture-patterns/poc-catalogo-bim-dinamico-aprendizados.md`,
`docs/plano-produto-dinamico.md` (seção 13) e levar duas coisas desta sessão:

1. **URL content-addressed para assets de storage** — o padrão certo com CDN na frente
   (seção 4). O `must-revalidate` daqui é o suficiente-para-POC, não o alvo.
2. **Visibilidade de catálogo** é requisito, não hardening (seção 6). Decidir antes de
   qualquer exposição de rede.

Armadilhas concretas:

- **A API não recarrega sozinha.** `pnpm dev:api` é `ts-node` puro, sem watch, e a porta é
  fixa em `main.ts:30`. Uma instância antiga na 4000 serve código velho e o `dev:api` novo
  morre com `EADDRINUSE` — mate o processo antes (`ss -tlnp | grep 4000`).
- **`pnpm thumb:regen` sem argumento não pega o Dancor**, apesar do que diz o docstring do
  `tools/regen-thumbs.ts`: pegou o import mais recente e regenerou os 856 do Silentium
  (~82 s). Passe o `importId` explicitamente.
- **Playwright está no `node_modules` da raiz do repo**, não no de `www/`. Script solto
  precisa de `NODE_PATH=/home/foltz/bilds-bim-3d/node_modules`.
