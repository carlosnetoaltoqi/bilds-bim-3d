# S4.4 — Miniaturas idênticas ao viewer 3D (Playwright + harness.html)

**Data:** 2026-08-30 · **Sessão do plano:** S4.4 (não prevista no plano original — nasceu da pendência da S4.3) · **Status:** concluída
**Commits:** ver `git log` a partir de `d042660`

## 1. O que era para fazer

Substituir o rasterizador software (`www/tools/thumb-rasterizer.ts`, Abordagem B do
ADR-003) por Playwright + `templates/thumbs/harness.html` no `thumb-worker.ts` da API
NestJS, para que a miniatura saia do **mesmo Three.js** que o viewer 3D usa.

Critério de aceite, de `docs/solutions/architecture-patterns/thumb-qualidade-identica-ao-viewer.md`:

1. Thumb do worker visualmente idêntico ao render do viewer 3D
2. Import Dancor (13 produtos) gera todos os thumbs sem erros
3. Tempo total < 30 s para 13 produtos
4. Thumbs aparecem corretamente no catálogo (`LazyBimCard`)

## 2. O que foi feito

**`templates/thumbs/harness.html`** — extraída `window.renderThumbFromData(data, W, H, mime, quality)`,
que recebe o objeto `{pos, col, idx}` já em memória e é a única função que toca WebGL.
`window.renderThumb(url, …)` (usada pelo pipeline estático) virou um wrapper: `fetch` +
delegação. Nenhuma mudança de material, luz ou câmera — os dois consumidores rendem a
mesma imagem.

**`www/tools/thumb-rasterizer.ts`** — reimplementado sobre Playwright. Mesmo nome de
arquivo e mesma assinatura pública (`renderThumbTs(data, width?, height?) → Promise<Buffer>`),
implementação inteiramente nova:
- `getSession()` — singleton por processo: servidor HTTP efêmero (`listen(0)`) sobre a
  raiz do repo + `chromium.launch(SWIFTSHADER_ARGS)` + página no harness
- `renderThumbPlaywright(data, w, h)` — serializa a geometria como **string JSON** e
  chama `renderThumbFromData` dentro da página; devolve o WebP decodificado da data URL
- `closeThumbRenderer()` — fecha browser e servidor; obrigatório antes de `process.exit()`
- Renders serializados numa fila (um único contexto WebGL por processo)
- Playwright resolvido de `bilds-bim-3d/node_modules/` quando não está no workspace

**`www/tools/thumb-rasterizer-sw.ts`** (novo, era o `thumb-rasterizer.ts`) — o rasterizador
software, agora histórico. `renderThumbTs` → `renderThumbSw`. Só `measure-thumbs.ts` o
importa, para manter reprodutível a comparação A × B que originou o ADR-003.

**`www/apps/api/src/importacoes/thumb-worker.ts`** — laço envolvido em `try/finally` com
`await closeThumbRenderer()`. Docstring atualizada. Interface IPC inalterada.

**`www/tools/regen-thumbs.ts`** — importa `closeThumbRenderer` e o chama no fim.

**`www/package.json`** — `thumb:regen` passou a repassar o argumento:
`sh -c '… regen-thumbs.ts "$@"' --`. Antes o `importId` virava `$0` do `sh` e era
descartado silenciosamente (limitação registrada na S4.3, agora corrigida).

## 3. O que foi verificado — e como

**Critério 1 — fidelidade ao viewer.** Renderizada a mesma geometria com o
`buildScene()`/câmera do `bim-viewer-engine.ts` sobre o Three.js **r185** do app web
(448×324, PNG sem perdas), e comparada por PSNR com o WebP que o worker grava:

```
produto                              | novo × viewer | antigo × viewer
2cv-t-220-380v-inc-flg-ir3           |      47,69 dB |        26,81 dB
20cv-2-1-2-t-4v-inc-flg-ir3          |      47,09 dB |        26,94 dB
4cv-2-1-2-t-4v-inc-ir3               |      47,55 dB |        27,75 dB
```

47 dB é o piso imposto pela compressão WebP q=0,85 — o render em si bate. Lado a lado no
browser a diferença antigo/novo é gritante: o antigo é uma silhueta chapada, o novo tem
o sombreamento e o relevo do viewer.

**Critério 2 — import completo pela API real:**

```bash
TOKEN=$(curl -s -X POST localhost:4000/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"…","password":"…"}' | jq -r .token)
curl -s -X POST localhost:4000/importacoes -H "Authorization: Bearer $TOKEN" \
  -F "file=@input/Dancor/pecas_dancor_bombas_incendio_2026_04.1.aq"
# → {"importId":"59c32b93-6d79-4fbb-928a-ee5a7add3114","status":"recebido"}
# → status publicado, productCount 13
```

13/13 arquivos em `storage/bim/thumbs/59c32b93-…/`, 13/13 documentos com `thumbKey`
não-nulo, zero mensagens `{type:'error'}`.

**Critério 3 — tempo.** Import publicado às 21:32:44,1; primeira thumb 21:32:45,8;
última 21:32:50,5. **~6,3 s para 13 produtos.** A primeira paga a subida do Chromium
(~1,2 s); as demais ficam entre 220 e 470 ms.

**Critério 4 — catálogo.** `http://localhost:3000/dancor/bomba-de-combate-a-incencio`
com Playwright: 13 cards, 13 `<img>`, todas com `src` em `localhost:4000/thumbs/…` —
nenhum card caiu no render dinâmico do `LazyBimCard`.

**Os dois consumidores do harness produzem o mesmo arquivo — byte a byte.** Rodado
`scripts/thumbs.mjs` (pipeline estático) sobre duas geometrias que também existem no
import da API, os WebP têm o **mesmo MD5**:


**Sem processo órfão:** `ps aux | grep chromium` vazio depois do worker sair.

**Typecheck:** `pnpm --filter api exec tsc -p tsconfig.json --noEmit` — só o erro

## 4. Decisões tomadas

**Servidor HTTP efêmero em vez de `file://`** (o plano previa `file://`). O harness
importa o Three.js como módulo ES via importmap, e o Chromium recusa `import` sobre
`file://` por CORS. `listen(0)` em `127.0.0.1` — nunca colide com a API (4000) nem com
o web (3000). É o mesmo servidor que o `thumbs.mjs` já subia; nada de novo no repo.

**Geometria vai como string JSON, não como objeto.** Essa foi a decisão que definiu se o
critério 3 passava. Ver seção 6.

**Manter o nome `thumb-rasterizer.ts`.** O arquivo trocou de implementação; o nome e a
assinatura ficaram para não obrigar mudança em quem importa. O software rasterizer virou
`-sw` em vez de ser apagado, porque `measure-thumbs.ts` é o registro reproduzível do
ADR-003 e perderia o sentido sem ele.

**Não alinhar a versão do Three.js.** O harness usa o vendor do repo (r170), o viewer usa
r185. Medido: PSNR 71 dB entre os dois — imperceptível. Aliasar o servidor para servir o
r185 traria uma segunda cópia do Three.js no caminho de render e um caminho diferente do
pipeline estático, exatamente a divergência que o harness existe para impedir. Registrado
na seção 5 do doc de arquitetura.

**Um browser por processo worker, fechado no `finally`.** Amortiza a subida sobre o lote
e evita órfão. O custo é ~200 MB de Chromium por worker — o alerta sobre
`MAX_THUMB_WORKERS` do doc de arquitetura continua valendo.

## 5. O que NÃO foi feito, e por quê

**Regenerar as 856 thumbs da Amanco.** O catálogo Amanco não está no banco nem no disco
desta máquina (`storage/bim/` só tem o import Dancor). Quando voltar, `pnpm thumb:regen <importId>`
resolve — a ~400 ms cada, ~6 min.

**Cache-busting no `GET /thumbs/:productId`.** O ETag deriva só do `thumbKey` e o
`Cache-Control` é `immutable`. Import novo gera `importId` novo → `thumbKey` novo → URL
nova, então o fluxo normal está correto. Só o `regen-thumbs` sobre o *mesmo* import
esbarra nisso: o browser continua servindo a imagem velha do cache. É uma armadilha de
verificação, não um bug de produção — está registrada no `CLAUDE.md`. Mexer no controller
seria escopo além do pedido.

**Paralelizar os renders.** Um contexto WebGL por processo; paralelizar exigiria N páginas
ou N browsers. A 470 ms por thumb, com fila serial, não é o gargalo da POC.

**`page.screenshot()` em vez de `toDataURL`.** `toDataURL` é o que o pipeline estático já
usa e mantém os dois caminhos idênticos; screenshot traria o compositor do browser para
dentro do resultado.

## 6. Surpresas — onde a documentação estava errada

**A estimativa de performance do doc de arquitetura estava invertida.** Ele previa
"~60–100 ms por thumb (WebGL vs software)" contra 130–170 ms do rasterizador software.
A primeira implementação, seguindo o plano ao pé da letra (`page.evaluate(d => …, geoData)`),
deu **~2 200 ms por thumb** — 24,5 s no lote de 13, quase estourando o critério de 30 s.

A causa não é o WebGL: é o serializador de argumentos do Playwright, que anda o grafo do
objeto — e a geometria é um array de centenas de milhares de números. Medido na mesma peça
de 4,8 MB:

| Forma | Tempo |
|---|---|
| argumento como objeto | ~2 200 ms |
| argumento como string JSON, `JSON.parse` dentro da página | ~370 ms |
| (dos quais o render WebGL propriamente dito) | ~120 ms |

`JSON.stringify` no Node custa 40 ms; `JSON.parse` na página, 13 ms. Passar a string
levou o lote de **24,5 s para 6,2 s**. O render WebGL real (~120 ms) está sim na ordem
de grandeza que o doc previa — o que o doc não previu foi o transporte.

Corrigido em `docs/solutions/architecture-patterns/thumb-qualidade-identica-ao-viewer.md`,
seção 6.

**O `thumb:regen` nunca recebeu o `importId`.** A S4.3 registrou isso como limitação e
regenerou por script inline. A causa é `sh -c 'cmd' arg`, onde `arg` vira `$0` e não `$1`.
Corrigido no `www/package.json` com `"$@"` e um `--` de placeholder para o `$0`.

**O import ativo não é o `5c60cb4e` do `CLAUDE.md`.** Nesta máquina o storage tinha o
import `2decd045` (13 produtos Dancor); depois desta sessão é o `59c32b93`. O `CLAUDE.md`
foi corrigido.

1. `docs/solutions/architecture-patterns/poc-catalogo-bim-dinamico-aprendizados.md`

3. `docs/plano-produto-dinamico.md`, seção 13

Armadilhas concretas que você vai encontrar:

- **Nunca passe geometria como objeto para `page.evaluate`.** Sempre string JSON. É 6×.
- **`closeThumbRenderer()` antes de qualquer `process.exit()`** — senão o servidor HTTP
  prende o event loop e o Chromium fica órfão.
- **Ao regenerar thumbs do mesmo import, o browser serve a versão em cache** — o ETag
  deriva do `thumbKey` e o `Cache-Control` é `immutable`. Use hard reload ou intercepte
  o request.
- Em WSL/container os flags SwiftShader são obrigatórios; sem eles o WebGL não inicializa
  e *todas* as geometrias falham de uma vez.
