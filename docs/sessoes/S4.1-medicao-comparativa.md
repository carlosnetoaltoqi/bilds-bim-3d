## 2. O que foi feito

escrito nem commitado — o entregável é este registro.

**Servidores usados:**
- Modelo POC (banco): API NestJS em `localhost:4000` + Next.js SSR em `localhost:3000`
  — ambos já estavam em execução no baseline.
- Modelo estático (CDN): `python3 -m http.server 8080` servindo
  `output/preview/bombas-incendio/` (catálogo Dancor gerado pelo pipeline Python).

**Dados de entrada do modelo banco:**
- Atlas: 13 produtos Dancor no catálogo `bomba-de-combate-a-incencio`, import ativo
  `563e5794` (sem deduplicação de vértices).
- Storage: `www/storage/bim/geo/563e5794/` (13 arquivos, 182.7 MB total).
- Thumbs: 13 WebPs gerados pelo rasterizador TS em S2.4.

**Dados de entrada do modelo estático:**
- `output/preview/bombas-incendio/` — HTML com `const CATALOG = {...}` embutido,
  `data/*.json` (13 arquivos, 44.7 MB total). Sem thumbnails pré-renderizados
  (output/thumbs/ é gitignored).

## 5. Respostas às 5 perguntas da seção 1

### Pergunta 1 — O catálogo dinâmico funciona?

**Sim.** 13 produtos Dancor gravados no MongoDB com `geoKey` e `thumbKey`, geometria
em disco via `GeometryStore`, página pública SSR renderizando com viewer 3D. A amarração
arquivo↔registro funciona: `GET /geometrias/:id` retorna o buffer correto em 36–46ms.

**Ressalva:** o import ativo não rodou deduplicação (geos com 14 MB vs 3.4 MB com dedup).
O código de dedup existe e funciona (import `5c60cb4e` prova), mas o catálogo ativo
aponta para o import `563e5794` (feito antes da implementação). Para S4.2, considerar se
valeria um re-import como dado de referência limpo.

### Pergunta 2 — O parse do .aq roda no servidor?

**Sim, em TypeScript** (ADR-002). 13 produtos Dancor parseados em 658ms vs ~39s do
worker Python. O worker faz `child_process.fork()` com timeout de 5 min.

### Pergunta 3 — As miniaturas sobrevivem à mudança?

**Sim** (ADR-003). Rasterizador TS (Abordagem B): 65ms/geo, 4.3 KB/WebP, sem Chromium.
Todos os 13 produtos Dancor têm `thumbKey` no Atlas e `GET /thumbs/:id` retorna HTTP 200.
Diferença visual vs PBR: aceitável para cards de catálogo (ver seção 13 do plano).

### Pergunta 4 — A página fica boa lendo do banco?

**Sim, com custo.** A página renderiza corretamente — 13 produtos, viewer 3D funcional,
filtros por série. O custo é no TTFB:

- SSR + MongoDB: 177–254ms vs ~50ms de um CDN estático
- Bytes iniciais: ~129 KB vs ~100 KB (diferença desprezível)
- Geo por modal (com dedup): equivalente ao estático

O TTFB de 200ms é administrável. Em produção, SSR com HTTP Cache-Control permite que
o CDN sirva o HTML gerado, reduzindo o overhead para zero no cache hit.

### Pergunta 5 — Isso escala?

**Projeção** (1 catálogo = 13 produtos Dancor):

| Escala | Banco (bim_products) | Geo em disco (com dedup) | Thumbs em disco |
|---|---|---|---|
| 1 catálogo (Dancor) | 13 documentos | 44.7 MB | ~56 KB |
| 10 catálogos | ~130 docs | ~447 MB | ~560 KB |
| 50 catálogos | ~650 docs | ~2.2 GB | ~2.8 MB |
| 200 catálogos | ~2.600 docs | ~8.9 GB | ~11 MB |

O banco escala facilmente — 2.600 documentos é trivial. O limitante é o disco/S3:
200 catálogos demandam ~9 GB de geo. Em S3 (~$0.023/GB/mês) isso custa ~$0.21/mês.

A Amanco (856 produtos, import com dedup) gerou 248 MB. Se a média for 250 MB por
catálogo, 200 catálogos = 50 GB → $1.15/mês. Viável.

## 6. Surpresas — onde a documentação estava errada

**Import ativo sem dedup.** O plano e o CLAUDE.md não registravam que o catálogo Dancor
ativo (`563e5794`) foi importado antes da implementação do `dedupBuffers` em
`parse-worker.ts`. A sessão S3.2b implementou o dedup, mas o catálogo ativo já existia
e não foi re-importado. Resultado: geo files 4× maiores que o esperado.

**Isso não precisa ser corrigido aqui** (sessão de medição, não de código). Mas S4.2
deve documentar isso como um caso a resolver na reconstrução: o sistema precisa de uma
rota de re-processamento para imports legados.
