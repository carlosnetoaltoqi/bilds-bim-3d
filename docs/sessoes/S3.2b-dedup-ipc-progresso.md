### Mudança 2 — Fix de flush IPC (bug crítico)

```typescript
// ANTES — process.exit(0) imediato descartava o payload em transmissão:
process.send!(result);
process.exit(0);

// DEPOIS — sai só após o flush ser confirmado pelo kernel:
process.send!(result, () => process.exit(0));
```

O mesmo fix foi aplicado no caminho de erro (callback de `process.exit(1)`).

- `fetch()` não expõe `upload.onprogress`; migrado para `XMLHttpRequest`.
- `uploadPct` state (0–100) alimenta barra de progresso animada (CSS gradient + `transition`).
- Botão exibe `"Enviando… X%"` enquanto `uploadPct < 100`, depois `"Processando…"`.

### Fix de IPC

Antes do fix: import de 856 produtos ficava preso em `parseando` após o worker logar
"PRONTO". O `child.on('message')` nunca disparava — payload de vários KB descartado pelo
buffer IPC antes do exit. Confirmado: callback `() => process.exit(0)` resolve.

Para Dancor (13 produtos, payload pequeno): funcionava antes do fix (flush síncrono na
prática). O bug só manifestou na Amanco (856 produtos).

### Progresso de upload

Upload do Amanco (393 MB): barra cresce de 0→100% durante o envio. Em `100%` o label
muda para "Processando…" enquanto o worker processa.

## 4. Decisões tomadas

**`process.send!(result, callback)` em vez de `await`-ável.** A API do Node.js IPC não
é `Promise`-based — o callback é a única forma de garantir flush antes do exit. A API
garante que o callback só dispara após o kernel confirmar a entrega do dado ao pipe.

**Float32 bit-cast como chave.** Igual ao `dedup.py` Python. A chave inteira (uint32 da
representação IEEE 754) é exata e comparável como string sem float imprecision. Alternativa
(arredondar para N casas decimais) seria menos fiel ao comportamento do Three.js.

**XHR em vez de fetch.** `fetch` não tem `upload.onprogress`. XHR tem `xhr.upload.onprogress`
com `ev.loaded / ev.total`. A Promise é embrulhada manualmente para manter a chain `.then`
existente.

## 5. O que NÃO foi feito, e por quê

**Banco de progresso intra-`gravando`.** O worker já gravou tudo antes de retornar — o
MongoDB insert é posterior e rápido (~1 s para 856 produtos). Granularidade não justifica
a complexidade.

**Barra de progresso de parse.** O worker roda em processo isolado; passar progresso via
IPC exigiria mensagens parciais antes do resultado final — mudança maior de protocolo.
Para S3.3 não é necessário.

## 6. Surpresas — onde a documentação estava errada

**Deduplicação ausente no pipeline dinâmico.** O CLAUDE.md e o plano não documentavam
que `parse-worker.ts` não aplicava dedup. Os arquivos de geometria eram 3–5× maiores
que os do pipeline estático. Corrigido agora — a documentação existente sobre o dedup
era do `scripts/dedup.py` (pipeline Python); a equivalência TypeScript estava implícita
mas nunca implementada.

**Bug de IPC não documentado.** O comportamento de `process.send!()` + `process.exit()`
para payloads grandes não estava descrito em lugar algum. É um comportamento não-óbvio
do Node.js: para payloads pequenos (Dancor, 13 produtos) o flush é síncrono na prática;
para payloads grandes (Amanco, 856 produtos) o exit descarta o buffer antes do kernel
confirmar. Agora documentado aqui e no `CLAUDE.md`.
