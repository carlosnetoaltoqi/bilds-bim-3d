## 4. Decisões tomadas

**JWT no body (não cookie) na resposta da API NestJS.** O NestJS retorna `{ token }` em
JSON. O Next.js route handler `/api/auth/login` é quem define o cookie httpOnly para o
domínio `:3000`. Isso resolve o problema de portas diferentes em dev (cookie do `:4000`
não é enviado para `:3000`). Em produção, API e web teriam o mesmo domínio — o padrão
seria diferente. Para a POC é o caminho mais simples.

**`Authorization: Bearer` no header da API.** O AuthGuard lê apenas o header, não cookie.
Os route handlers do Next.js adicionam o header ao chamar a API. Separação limpa.

**Logo via `fs.writeFileSync` diretamente.** O GeometryStore foi desenhado para geometrias
(JSON). Logos são blobs binários de outro tipo; usar o mesmo interface seria possível mas
desnecessário. O path `STORAGE_PATH/logos/{companyId}.ext` basta para a POC.

**Um usuário, uma empresa.** O ownerId é o `sub` do JWT (o email do usuário semente). O
endpoint `GET /empresas/minha` busca por `{ ownerId }`. Sem RBAC, sem lista de empresas —
cobre o critério de S3.1.

**`customUrl` sanitizado na API.** O endpoint aplica `.toLowerCase().replace(/[^a-z0-9-]/g, '-')`
ao `customUrl` recebido. O frontend mostra o slug auto-gerado mas o servidor é quem canoniza.

## 5. O que NÃO foi feito, e por quê

**Rate limiting no endpoint de login.** Um usuário, sem entrada hostil — item da seção 13
da POC.

**Refresh de token / expiração na UI.** O JWT expira em 7 dias. Na expiração, o cookie
ainda existe mas as chamadas à API retornam 401. A UI não trata isso — o usuário vê um
estado quebrado até fazer logout manual. Não vale a complexidade para a POC.

**Teste automatizado das rotas.** Verificado manualmente conforme seção 3.

**Validação de formato do customUrl no frontend.** O frontend já gera o slug, mas não valida
comprimento mínimo ou conflito em tempo real. O servidor rejeita com 409 ou 400 e o erro
aparece na tela.

## 6. Surpresas — onde a documentação estava errada

**Nenhuma.** O estado do repositório estava exatamente como descrito no registro S2.4 e
no CLAUDE.md.

**Armadilha encontrada: `Express.Multer.File` sem `@types/multer`.**
Ao usar `FileInterceptor` do `@nestjs/platform-express`, o tipo `Express.Multer.File`
precisa de `@types/multer` instalado explicitamente no pacote da API — mesmo que o multer
venha como dependência transitiva. Sem isso, `ts-node` falha com `error TS2694: Namespace
'global.Express' has no exported member 'Multer'`. Solução: `pnpm add --filter api -D
@types/multer`. Registrado aqui para a S3.2 (que também usa `FileInterceptor`).
