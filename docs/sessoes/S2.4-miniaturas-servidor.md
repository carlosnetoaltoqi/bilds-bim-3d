## 1. O que era para fazer

Worker de miniaturas isolado do fluxo de upload, medindo os dois caminhos da 7.4:
Playwright + Chromium + SwiftShader (tempo por geometria, memória, tamanho de imagem)
e o rasterizador TS. Pronto quando há números para os dois caminhos e um ADR dizendo
qual sai mais barato em produção.

## 2. O que foi feito

**Novos arquivos:**

- `www/tools/thumb-rasterizer.ts` — rasterizador TS puro, sem browser. Projeta vértices
  em perspectiva, rasteriza triângulos com z-buffer e flat shading, escreve RGBA via
  ffmpeg (`pipe:0 → pipe:1 → libwebp`). Câmera, luzes e fundo idênticos ao `harness.html`.
  Exporta `renderThumbTs(data, w?, h?): Promise<Buffer>`. Dimensões padrão: 448×324 px.

- `www/tools/measure-thumbs.ts` — script de medição comparativa. Lê produtos do Atlas
  via MongoDB, mede a Abordagem B (rasterizador TS) e a Abordagem A (Playwright +
  Chromium + SwiftShader), imprime tabela Markdown. Rodado com `pnpm thumb:measure`.

- `www/apps/api/src/importacoes/thumb-worker.ts` — worker fork para geração de miniaturas.
  Recebe `{ products, storagePath, importId }` via IPC. Para cada produto: lê o geo JSON,
  chama `renderThumbTs`, grava em `storagePath/thumbs/{importId}/{productId}.webp`, envia
  `{ type: 'thumb', productId, thumbKey }`. Ao concluir envia `{ type: 'done', count }`.
  Erros individuais são reportados e o worker continua (`{ type: 'error', ... }`).

**Arquivos modificados:**

- `www/apps/api/src/importacoes/importacoes.service.ts` — após `status: 'publicado'`,
  dispara `this.spawnThumbWorker(importId, productDocs.map(...))` fire-and-forget.
  `spawnThumbWorker`: faz `child_process.fork('thumb-worker.ts')`, envia o input via IPC,
  escuta mensagens `type: 'thumb'` → `productModel.findByIdAndUpdate(productId, { thumbKey })`.
  Falhas são silenciadas — miniaturas são opcionais.

- `www/package.json` — adicionado script `thumb:measure`.

### Medição comparativa (pnpm thumb:measure)

Rodado com 39 produtos do Atlas (múltiplos imports Dancor):

```
| Abordagem | Média ms/geo | Heap Δ MB | KB/WebP |
|-----------|-------------|-----------|---------|
| B (TS)    |          65 |      -6.2 |     4.3 |
| A (PW)    |         240 |      -1.9 |     5.5 |
```

O heap Δ negativo da B reflete GC entre medições; o pico real é ~30 MB por geometria
(os arrays pos/col/idx são coletados entre renders). A Abordagem A usa Chromium em

## 4. Decisões tomadas

**ADR-003: Abordagem B (rasterizador TS).** 3,7× mais rápido, 20% imagens menores, sem
dependência de Chromium no pod. A qualidade visual (flat shading com ambient + 2 luzes)
é suficiente para miniaturas de catálogo. A Abordagem A é superior em fidelidade visual
(PBR idêntico ao viewer), mas exige ~1,5 GB de imagem Docker e startup de 2-5 s antes
do primeiro render — custo operacional alto demais para um worker fire-and-forget.

**Fire-and-forget, sem bloquear o upload.** O import fica `publicado` em ~10 s; as
miniaturas chegam em ~1 s depois. Produtos sem `thumbKey` retornam 404 em
`GET /thumbs/:id` — o controller já tratava isso.

**Uma miniatura por produto (não por geometria).** O thumb-worker salva
`thumbs/{importId}/{productId}.webp` — um arquivo por `_id` de produto. Isso difere
do pipeline estático (que faz um por geometria única). Aqui, produtos que compartilham
geometria geram arquivos duplicados em disco. Aceitável: a Dancor tem 13 produtos e 13
geometrias únicas; para catálogos com geometria compartilhada, otimizar quando necessário.

**ffmpeg para WebP, não sharp.** `sharp` não está instalado no workspace. O ffmpeg com
`libwebp` está disponível em `/home/foltz/.local/bin/ffmpeg`. A qualidade padrão usada
é `libwebp` default (equivalente a q=80 aproximadamente).

**Sem `-vf vflip` no ffmpeg.** O rawvideo rgba no ffmpeg é top-to-bottom por padrão,
igual ao layout do buffer do rasterizador (py=0 = linha de cima). Adicionar vflip
inverteria a imagem.

## 5. O que NÃO foi feito, e por quê

**Otimização de memória do rasterizador.** O pico de ~30 MB/geo é gerenciável para
renders sequenciais. Usar `Float64Array` na projeção reduziria o overhead de GC.
Postergado — não impacta a POC.

**Deduplicação de arquivos de miniatura (geometrias compartilhadas).** Para a Dancor
não é problema (1 produto = 1 geometria). Se um futuro catálogo tiver 800 produtos e
400 geometrias, o worker geraria 800 arquivos idênticos par a par. A solução seria
gerar por geometria e criar symlinks, mas não vale a complexidade agora.

**Teste automatizado do worker fork.** Verificado manualmente com fork direto. Um teste
unitário para o thumb-worker requereria mockar o processo filho ou rodar o fork em ci
— escopo para S3.x ou revisão posterior.

## 6. Surpresas — onde a documentação estava errada

**API precisava ser reiniciada.** O plano dizia que o API do S2.3 estava em execução.
Estava — mas rodando o código do commit `cb4f110` (S2.3), sem o `spawnThumbWorker` desta
sessão. O upload funcionou (HTTP 201, publicado), mas os thumbs não foram gerados porque
o código fire-and-forget não existia no processo em execução. Solução: matar o processo
antigo (PID 2087, iniciado às 09:55) e subir o API com o código novo. **Isso não é
problema em produção** — a API sempre sobe com o código do commit atual.

**playwright não é importado em `require()` do path absoluto diretamente do contexto
de teste.** Para a Abordagem A, o path correto do playwright é
`bilds-bim-3d/node_modules/playwright` — dois níveis acima de `www/tools/`, não três.
Três levaria para `/home/foltz/node_modules/` (inexistente).

**createServer vem de `node:http`, não `node:fs`.** Erro de digitação no `measure-thumbs.ts`
inicial. Corrigido antes de rodar.
