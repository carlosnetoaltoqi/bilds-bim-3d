## 1. O que era para fazer

Port TypeScript de `scripts/oq3d.py` + `scripts/read_aq.py` para **uma** biblioteca
(Dancor), atravessando os dois riscos da seção 7.3:

- `CAST AS BLOB` + decodificação manual de cp1252 sem `text_factory` do Python
- Comparação **semântica** com a saída Python elemento a elemento

**Pronto quando:**
- A Dancor gera em TS o mesmo catálogo que em Python sob comparação semântica
- O parser rejeita com `OQ3DError` blob truncado / contagem > buffer / assinatura ausente,
  sem alocar buffer proporcional à contagem declarada
- O ADR registra o custo real do port contra o do worker de S2.1

## 4. Decisões tomadas

### D1 — `node:sqlite` com `CAST(col AS BLOB)` em vez de `text_factory`

`DatabaseSync` (Node v24, sem flags) retorna `Uint8Array` para colunas BLOB.
`TextDecoder('windows-1252')` decodifica cp1252 sem exceção nos 5 bytes indefinidos
(0x81, 0x8D, 0x8F, 0x90, 0x9D) — comportamento mais robusto que o fallback latin-1
do Python. Todo `SELECT` de coluna de texto usa `CAST(col AS BLOB) AS nome_blob`.

### D2 — `OQ3DError` tipado, sem alocação antes da validação

Onde o Python retorna silenciosamente (`return off`), o port lança `OQ3DError`
com mensagem descritiva. A validação de `nCoord × 8` e `nIdx × 4` contra
`buf.length` acontece **antes** de qualquer `new Array(nVerts)` — sem alocar
memória proporcional à contagem maliciosa.

### D3 — Tolerância numérica de 1e-10 relativo na comparação semântica

Python usa numpy (BLAS/LAPACK, potencialmente FMA). TypeScript usa aritmética
escalar IEEE 754. A mesma sequência de operações matriciais pode divergir em
1-2 ULPs (~10⁻¹⁵ relativo com transforms compostos). A tolerância 1e-10 rejeita
erros reais (CM_TO_M ausente → 100×, eixo trocado → sinal errado) e aceita
ruído numérico de precisão de máquina. Dos 13 produtos, 10 tinham divergências
de 1 ULP antes da tolerância; 3 (produtos 8, 12, 13) passavam exatamente.

### D4 — ADR-002: porta TS, não worker Python (ver plano seção 9)

Resumo da comparação:

| Dimensão | Formato A (port TS, S2.2) | Formato B (worker Python, S2.1) |
|---|---|---|
| Tempo de parsing | **658 ms** | ~39 000 ms |
| Memória RSS delta | 422 MB | **189 MB** |
| Memória heap delta | 241 MB | **119 MB** |
| Latência na cadeia | zero spawn | 2–5 s de cold start |
| Dependências de produção | só Node | Python + venv + numpy |
| Manutenção a longo prazo | um código, mas dois | um código |
| Segurança de tipos | OQ3DError tipado | exceções genéricas |

Velocidade: **59× mais rápido**. Memória: **2.2× mais** (parse em memória de arrays JS vs
streaming implícito do numpy + GC Python). O aumento de memória é atribuído à
representação intermédia — arrays de tuplas JS (`Array<[number,number,number]>`) antes
de achatar em `Float32Array`. Candidato natural a otimização em S2.3/S2.4 se a memória
virar gargalo.

**Decisão:** prosseguir com o port TS (Formato A). O ganho de latência e a eliminação
da dependência de Python superam o custo de memória, que é gerenciável e otimizável.

## 5. O que NÃO foi feito, e por quê

- **ZIP dentro de `.aq`**: implementado em `aq-reader.ts` (`extractSQLiteFromZip`),
  mas **não testado** — Dancor é SQLite direto e era o único escopo desta sessão.
  A próxima sessão que processar uma biblioteca ZIP deve testar esse caminho.
- **Port de `build.py`** (geração de catálogo): fora do escopo desta sessão — S2.2
  era só o spike de viabilidade do port, não a integração completa.
- **Otimização de memória**: o port usa `Array<[number,number,number]>` em vez de
  `Float32Array` para representação interna. A memória TS (422 MB) > Python (189 MB)
  mas bem dentro do limite de um processo Node em produção. Não foi otimizado.

## 7. Onde a próxima sessão começa

**Próxima sessão:** S2.3 — Importação server-side e rotas de leitura.

**Pré-requisitos:**
- `pnpm smoke:geo` deve imprimir `smoke test passed`
- Atlas deve ter os 13 produtos da Dancor (gravados em S1.2)
- `www/.env` deve ter `MONGODB_URI`, `MONGODB_DB=bilds-bim-3d`, `STORAGE_PATH=../../storage/bim`

**Armadilhas concretas para S2.3:**

1. **`node:sqlite` é síncrono** — `DatabaseSync` bloqueia o event loop. Se S2.3 chamar
   `extractSimboloias` dentro de um handler NestJS, envolva em `worker_threads` ou mova
   para fora do ciclo de request. (Alternativa: usar o worker Python de S2.1 que já é
   processo separado.)

2. **ZIP dentro de `.aq` não testado** — a Dancor é SQLite direto. Se S2.3 processar
   outra biblioteca, primeiro confirme se o arquivo é SQLite ou ZIP antes de assumir.

3. **Memória do port** — o port TS usa ~420 MB RSS para os 13 produtos da Dancor.
   Em produção, com múltiplas importações simultâneas, pode ser necessário serializar.

4. **`OQ3DError` deve ser capturado no nível de importação** — produtos com blob
   inválido não devem derrubar a importação inteira. Capturar por produto, logar e
   continuar.

**Perguntas abertas para S2.3:**
- Usar o port TS (`extractSimboloias` + `toBuffers`) ou o worker Python de S2.1 no
  handler de upload? O ADR-002 recomenda TS, mas S2.3 deve confirmar que a memória
  não é problema com o tamanho real do `.aq`.
